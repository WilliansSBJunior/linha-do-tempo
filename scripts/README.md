# scripts/

Python 3 padrão (só stdlib; SQLite >= 3.37 com FTS5). Nenhuma dependência extra. Rode a partir da raiz do repo.

| Script | O que faz |
|---|---|
| `migrar.py` | Recria `data/linha-do-tempo.sqlite` a partir de `data/raw/` (confere `hashes.txt`), gera `data/dump.sql` e `data/relatorio-migracao.md`. Determinístico. |
| `validar.py [--db X]` | Integridade, contagens, órfãos e round-trip contra `data/raw/dados-caso-master-v2.json`; tema (toda relação/evento tem tema, regras de origem/canal valem em 100%, exceções aplicadas, toda entidade tem tema), fonte (URL -> evidência, `hash_texto`, corte só em vídeo, view `video`; fonte sem trecho é aviso) e teia <-> timeline (relações de mandato/filiação, fusões nos dois temas). Sai com código 1 em qualquer falha. |
| `exportar_json.py [--db X]` | Só lê o banco: escreve `data/{entities,teia,origens,series,mapa_indices,dossie,pares,temas}.json` e regenera `data/dump.sql`. Campos aditivos: `tema` em cada relação/EV/PREC de `teia.json` e EV de `origens.json`, `temas` em cada entidade de `entities.json`; em `teia.json`, `fontes` em cada `E[].r` (`[{url, veiculo, tipo, titulo, data, qualidade}]`, oficiais/decisões primeiro, depois reportagem, depois o resto) e em cada `EV` (sem `qualidade`), e `sat` nos nós satélite (`{rot, desc, fontes}`: a relação `N[i].fam_de`/`lig_de` com a descrição atual do banco; `validar.py` a confere contra o banco e a deixa fora do round-trip com o raw); `temas.json` traz contagens e a pertinência (relações por id, eventos por id, entidades pela view). `dossie.json` e `pares.json` têm o mesmo conteúdo do JSON embutido nas páginas (comparados com `data/raw/` pelo `validar.py`). |
| `importar.py [--db X] [--force]` | Reconstrói o sqlite a partir de `data/dump.sql` (é o que se faz depois de um `git clone`). |
| `extrair_violencia.py` | Uma vez só: extrai os literais JS de `paginas/violencia.html` (via Node) para `data/raw/violencia.json`. |
| `schema.sql` | DDL (desvios da proposta marcados `-- DESVIO:`). Modelo v2: `tema`/`relacao_tema`/`evento_tema`, view `v_entidade_tema`, `fonte` (+ view `video` de compatibilidade, `trecho.fonte_id`, triggers de corte/tempo). |
| `slug.py` | `slugify`, `SLUG_FIXO`, `alias_norm`, regra de nome base. |
| `fusoes.json` | Fusões de entidades aprovadas (`[{"de": "slug-velho", "para": "slug-novo"}]`); vazio por ora. |
| `comum.py` | Caminhos, normalização de URL, dump determinístico, FTS. |
| `curadoria.py` | Aplica `data/curadoria/*.json` depois da carga bruta (fusões, natureza, fontes da timeline, ligações evento-entidade, complementos, **relações de mandato/filiação, temas**) e contém as regras que geram parte deles; `inferir_temas_relacao` também é usado pelo MCP. |
| `gerar_curadoria.py [--so ...]` | Regenera os JSON derivados por regra (`eventos-natureza` (R1-R5), `brasil-fontes`, `brasil-complementos`, `evento-entidade-auto`, `mandato-oficial`) a partir de um banco temporário. Determinístico. `--so mandato-oficial` também escreve `data/relatorio-mandatos-oficial.md`. |
| `coletar_mandatos.py [--so camara\|senado\|presidencia] [--forcar] [--so-cache]` | Roda na máquina do usuário (rede): baixa mandatos/filiações das APIs da Câmara e do Senado e as páginas oficiais das presidências das Casas para `data/raw/oficial/` (congelado; só `camara.json`, `senado.json`, `presidencia.json` têm hash em `hashes.txt`, o `cache/` não; os três JSONs são produto da nossa própria coleta, então o hash é atualizado a cada rodada). `--so-cache` nunca vai à rede: usa só o cache e, sem cache, devolve o status `erro: sem cache`. Busca cada nome (o do banco e os aliases) até casar; homônimos são desempatados pela UF e pelas legislaturas que tocam os anos da pessoa. `PAGINAS` marca como `indisponivel` (com motivo, sem baixar nada) as páginas da Presidência da República que não são públicas. Preserva a seção "Como esta coleta foi feita" de `data/raw/oficial/RELATORIO.md`. Rodar depois de `migrar.py`/`importar.py` (lê nomes e aliases do banco). |
| `dossie_rel.py` | Carga relacional do dossiê (`dossie_par`, `previdencia_ente`, `pagamento`, `indicio_maquina`, `limite`) e de `pares.foruns` (`forum`). |

Fluxo normal:

```
python3 scripts/migrar.py && python3 scripts/validar.py && python3 scripts/exportar_json.py && python3 scripts/validar.py
python3 scripts/importar.py --force   # reconstrói o sqlite a partir do dump
python3 scripts/gerar_curadoria.py    # só quando mudar uma regra ou um arquivo escrito à mão em data/curadoria/ que alimente as regras
```

## data/curadoria/

Princípio: `migrar.py` recria o banco do zero a partir de `data/raw/` e **depois** aplica estes arquivos JSON (versionados e legíveis). Toda correção editorial entra aqui; ninguém edita o banco à mão. Dois tipos:

| Arquivo | Origem | O que faz |
|---|---|---|
| `eventos-fusoes.json` | à mão | `[{"manter": id, "fundir": [ids], "motivo": "..."}]`: funde eventos quase-duplicados (mesma data, mesmo fato). O mantido recebe a união de fontes e entidades, `peso` máximo e a natureza mais forte; os ids fundidos viram `evento_alias` (com `original_json`). Mesmo grupo = mesma `data`. |
| `eventos-candidatos.md` | à mão | Pares duvidosos que ficaram de fora, para decisão. |
| `dossie-entidades.json` | à mão | Vínculo texto livre do dossiê -> entidade (`mapa`, lista vazia = sem entidade), `justificativas` e `entidades_novas` (fundos de previdência sem nó). |
| `evento-entidade-regras.json` | à mão | Regras do casamento por alias (sobrenomes ambíguos, siglas, contextos barrados). |
| `eventos-natureza.json` | gerado | `[{"id", "natureza", "regra"}]` para eventos sem natureza; aplicado só onde `natureza_id IS NULL`. R1-R4 (canal `teia`) e **R5** (canais `brasil` e `violencia`: pelo `evidencia.tipo`/domínio das evidências com papel `sustenta`: oficial -> `documentada`; reportagem/relatório -> `reportada`; senão `nao_classificada`; fontes de `contexto` não contam), documentadas em `relatorio-migracao.md` (seção 10) e em `curadoria.REGRAS_NATUREZA_TEXTO`. Gerado por `gerar_curadoria.py --so eventos-natureza` (aceita também `--so natureza`), que aplica antes o `brasil-fontes.json` no banco temporário. |
| `eventos-natureza-manual.json` | à mão | `[{"id","natureza","justificativa"}]`: os eventos da teia que R1-R4 não pegam, lidos um a um (título, descrição, fontes) e classificados com julgamento conservador (`documentada` só com documento oficial/decisão ligado; `investigacao` = ato de PF/MPF/CPI/CVM/operação/busca; `reportada` = revelação ou fato noticiado sem documento oficial; `alegacao` = afirmação de uma parte sem confirmação). Aplicado por `curadoria.aplicar_natureza` **depois** do gerado e só onde `natureza_id IS NULL`. Uma entrada com `"natureza": null` é exceção explícita (o evento fica NULL; a justificativa é obrigatória). Não é tocado pelo gerador. `validar.py` exige zero eventos NULL fora dessa lista e regra/justificativa registrada para toda natureza aplicada. |
| `brasil-fontes.json` | gerado | Fontes dos eventos da timeline Brasil, vindas de `data/raw/dados-brutos-31-anos.json` (URLs por bloco-ano: `contexto`; `sustenta` quando o slug da URL toca o evento). |
| `brasil-complementos.json` | gerado | `ranking_empresa.receita_brl_bi` e `mandato.periodo_texto` do bruto, só onde o mapeamento é inequívoco. |
| `evento-entidade-auto.json` | gerado | Ligações `evento_entidade` com `papel='citado'` por alias. |
| `mandato-oficial.json` | gerado | Confronto de `mandato` com `data/raw/oficial/{camara,senado,presidencia}.json` (`--so mandato-oficial`; chave = entidade_id + cargo + início): `evidencias` (`dado_oficial` das APIs; `documento_oficial` das páginas das presidências das Casas), `confirmacoes` (cada uma com `confirmacao`: `legislatura` = a pessoa consta na API em alguma legislatura que toque o ano; `eleicao` = só consta na legislatura que começa em 1/fev do ano seguinte e o `motivo` da linha fala de eleição, ou seja, prova o mandato subsequente e não o exercício no ano; `pagina` = `presidente_camara`/`presidente_senado` pelo nome e pelo ano de início na página oficial), `complementos` (só campo NULL), `divergencias`, `sem_fonte` (presidente e vice: não há página pública), `nao_encontrados`. `curadoria.aplicar_mandato_oficial` preenche `mandato.evidencia_id` só onde está NULL, antes de `gerar_relacoes_mandato`, e as relações de mandato/filiação herdam a evidência. Relatório: `data/relatorio-mandatos-oficial.md`. |
| `mandato-correcoes.json` | à mão | `[{"entidade_id","cargo","inicio","campo","de","para","motivo","fonte_url"}]`: troca `partido`, `uf` ou `fim` de uma linha de `mandato` quando a fonte oficial prova o valor (hoje: Miro Teixeira deputado 2004, PT -> PPS, histórico da Câmara; e o `fim` de Lula, Alckmin, Temer vice e Hugo Motta, decididos na revisão das ressalvas). Aplicado por `curadoria.aplicar_mandato_correcoes` depois da carga e **antes** de `aplicar_mandato_oficial`/`gerar_relacoes_mandato`; falha se a linha não existe ou o valor atual não é `de`. `gerar_curadoria.py` também parte do banco já corrigido. |
| `entidade-aliases.json` | à mão | `[{"entidade_id","alias","motivo"}]`: aliases de grafia (`entidade_alias.tipo_alias='grafia'`, `origem='curadoria'`) acrescentados por `curadoria.aplicar_aliases`, por exemplo o nome parlamentar da API da Câmara ("Enéas", "Luís Eduardo", "Luiz Carlos Santos"). Nunca remove nem troca alias existente. Os aliases de grafia são usados por `coletar_mandatos.py` na busca por nome. |
| `temas.json` | à mão | Seed de `tema`, regras de atribuição a `relacao_tema`/`evento_tema` (por origem, canal, entidade, texto; `dentro_de`) e `excecoes` (falso positivo/ajuste por registro, com motivo). Aplicado por último em `migrar.py`; quem ficar sem tema vai para `a-classificar`. |
| `evidencias-adicionais.json` | à mão | Fontes pesquisadas para os eventos e relações que ficaram sem nenhuma evidência (`[{...}]`, uma entrada por alvo + URL). Alvo: `evento_id`, ou, para relação, `relacao_origem` + `relacao_origem_ref` (os ids de `relacao` são atribuídos na migração; esta chave é estável). Campos: `url`, `veiculo`, `tipo` (CHECK de `evidencia.tipo`), `titulo`, `data` (ano ou data; `null` se vazia), `trecho`, `nota` (ressalva do pesquisador), `qualidade` (`boa`/`fraca`; `fraca` exige `motivo_fraca`), `substituida_por` (fraca trocada por outra fonte: a entrada fica no arquivo como histórico e **não** é ligada ao alvo; a nova entrada `boa` traz `substitui: <url da fraca>`; substituição parcial mantém a fraca ligada, sem `substituida_por`, com a nota), e nas relações da teia `descricao_nova` e, quando a fonte descreve o vínculo diferente do rótulo do grafo, `divergencia_rotulo`. Aplicado por `curadoria.aplicar_evidencias_adicionais` (depois das relações de mandato/filiação, antes dos temas): cria a `evidencia` (URL normalizada; se já existe reaproveita sem mudar veículo/tipo), liga em `evento_evidencia` (rótulo = título) ou `relacao_evidencia` (papel `sustenta`) guardando `trecho_citado`, `nota` e `qualidade` na ligação (colunas aditivas do schema; NULL nas ligações antigas). Troca `relacao.descricao` por `descricao_nova` só quando a atual começa com "Vínculo" e contém "sem descrição na fonte"; nunca muda rótulo, tipo, subtipo nem descrição de evento. Relatório: `data/relatorio-evidencias-adicionais.md` (contagens, divergências de rótulo, fontes fracas para substituir, todas as ressalvas dos pesquisadores), escrito por `migrar.py`. `validar.py` exige zero eventos e zero relações publicadas sem evidência e confere o arquivo contra o banco. |
| `evento-correcoes.json` | à mão | Decisões sobre as ressalvas de `data/relatorio-evidencias-adicionais.md`. `correcoes`: `[{"evento_id","campo","decisao","de","para","motivo","ressalvas"}]`, substituição textual exata em `evento.titulo` ou `evento.descricao` (chave estável = evento_id + campo; um id fundido é achado por `evento_alias`). `de` tem de ocorrer **exatamente uma vez** no valor atual do campo; senão `curadoria.aplicar_evento_correcoes` aborta a migração com a lista dos problemas, sem aplicar nada. `ressalvas_mantidas_com_nota` lista os ids de ressalva aceitos sem mudar o banco (só contam no relatório); `fontes_fracas` é só uma nota. Os eventos corrigidos mudam o texto que `gerar_curadoria.py` lê: depois de editar este arquivo, rode `gerar_curadoria.py` e confira `evento-entidade-auto.json` (as ligações por alias derivam do texto). |
| `relacao-correcoes.json` | à mão | `periodos` (relações `origem='linha_do_tempo'`) e `vinculos_teia` (relações da teia), cada entrada `{"origem","origem_ref","alvo":{de,rotulo,periodo_inicio | de,para,rotulo},"decisao":"aceitar"\|"manter","de":{campo:valor atual},"para":{campo:valor novo},"motivo","ressalvas"}`. Chave estável = `origem` + `origem_ref` (`mandato:<id>`, `filiacao:<pessoa>:<partido>:<início>`, `N[<i>].fam_de`); `alvo` confere a identidade da relação e cada campo de `de` tem de valer o valor atual, senão a migração aborta sem aplicar nada (`curadoria.aplicar_relacao_correcoes`). Campos permitidos: `periodo_fim`, `descricao`, `subtipo`, `rotulo`, `tipo` (os CHECKs do schema valem). `manter` não muda nada e só entra no relatório. Os fins de mandato (Lula, Alckmin, Temer vice, Hugo Motta) são corrigidos em `mandato-correcoes.json` (campo `fim`), e as relações nascem certas; aqui `periodo_fim` só aparece nas filiações de Bolsonaro no PSL e de Alencar no PL, as únicas exceções que `validar.py` aceita (sobreposição com o mandato em vez de inclusão). Ambos os arquivos rodam depois das evidências adicionais e antes dos temas. Relatório: `data/relatorio-revisao-evidencias.md` (contagens, cada correção `de -> para` com motivo, itens mantidos), escrito por `migrar.py`; `validar.py` confere que todo `para` está no banco e `de` não, e que `tipo`/períodos respeitam os CHECKs. |
| `mandato-relacoes.json` | à mão | Rótulo por cargo, órgão de presidente/vice (`presidencia-da-republica`), mapa manual de partido e textos que não são filiação, para `gerar_relacoes_mandato` (relações `institucional` `mandato:<cargo>` e `filiacao`, `origem='linha_do_tempo'`, tema `brasil-ano-a-ano`). |

Tema, fonte e relações de mandato (modelo v2, seções 14 a 16 do `data/relatorio-migracao.md`): `temas.json` e `mandato-relacoes.json` são escritos à mão (o gerador não os toca). `data/*.json` derivam do banco: depois de qualquer escrita do MCP rode `exportar_json.py` antes de `validar.py`.

Os arquivos gerados são regenerados por `gerar_curadoria.py`; para corrigir um deles na mão, edite o JSON e **não** rode o gerador (ele sobrescreve), ou acrescente a exceção nas regras/arquivos escritos à mão. Após qualquer mudança em `data/curadoria/`: `migrar.py` -> `validar.py` -> `exportar_json.py` -> `validar.py`.

`data/raw/dados-brutos-31-anos.json` é a única adição ao raw nesta rodada (cópia exata de `projeto-json/dados-brutos-31-anos.json`, hash em `hashes.txt`).

Git versiona `data/dump.sql` e os JSONs; `data/linha-do-tempo.sqlite` fica no `.gitignore`.
Só o servidor MCP escreve no banco; estes scripts não gravam nele fora da migração (`exportar_json.py` e `validar.py` só leem).
`data/raw/` é cópia congelada dos dados de origem (não editar; `migrar.py` recusa rodar se um hash mudar).

## Decisões humanas (fila de revisão)

`migrar.py` reaplica automaticamente `data/curadoria/decisoes.jsonl` (gravado pelas ferramentas `revisar_*` do MCP e pela página local `ferramentas/revisao.html`, servida por `python3 scripts/servir_revisao.py`). Para reaplicar à mão ou num banco reconstruído por `importar.py`: `python3 scripts/aplicar_decisoes.py [--db ...]` (idempotente). Pule com `migrar.py --pular decisoes` se a função `main` for chamada com `pular=("decisoes",)`.
